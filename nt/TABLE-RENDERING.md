# 表格渲染：虚拟滚动 vs 分批追加

> 写于 2026-10-30 凌晨，用户说「等我想周全」。
> 这里只讲机制和取舍，不做决定。决定在产品那边。

---

## 一、虚拟滚动的本质

一句话：

> **它不是在「显示数据」，而是在「用一个假的滚动条，模拟一份比 DOM 大得多的列表」。**

DOM 里那二三十行不是你的数据，是**当前视口的一个投影**。数据在内存里，"滚动条" 由两个空行（spacer）撑出来。

### 机制拆解（`ui/render-transactions.js` 的旧实现）

```js
const total = rows.length + BLANK_ROWS;          // 逻辑总行数，比如 3040
const rowH  = 32;                                // 每行高度，必须固定
const start = floor(scrollTop / rowH) - 2;       // 视口上沿往下两行
const end   = ceil((scrollTop + viewH) / rowH) + 2;
```

1. 算 `start / end` —— 当前视口该看到第几行到第几行
2. 顶部插一个高度 `start × rowH` 的 `<tr>`，底部插 `(total − end) × rowH` 的 `<tr>`
3. 中间真正渲染 `rows[start..end]`
4. 滚一下 → 重算 → **把中间那二三十行全部销毁，重新造**

第 2 步的空行就是那个「假滚动条」：它让 `scrollHeight` 等于 3040 × 32px，于是滚动条的比例看起来像有 3000 多行。

**第 4 步是全部代价的来源**：`replaceChildren(frag)` 会把屏幕上的每一行换成新的 DOM 节点。

## 二、三条必然结果

这三条不是「实现没写好」，是模型的直接推论。

### ① DOM 行是临时的，任何重建都换一批新的

触发重建的有：滚动、`render()`、切 tab 回来、窗口 resize、行高参数变化。
每一次，屏幕上的行都是**刚造出来的**，不是原来那一批。

### ② DOM 上的一切编辑态都是易失的

- 输入框里**还没提交**的文本
- 焦点在哪一格、光标在第几个字符
- 中文输入法的组合态（拼音还没上屏那一段）
- 框选的范围、拖选到一半的手势
- 滚动锚点（用户正在看哪一行）

虚拟滚动对这些都是「无所谓」的，因为它假设列表是**只读展示**。

### ③ 每个 DOM 细节都要代码自己维护

- `data-id` 每次重建要重新赋
- 斑马纹不能用 CSS `nth-child`（窗口起点一变，奇偶相位整排翻转，滚动时条纹会「往下滑一下」），必须按数据下标记类
- 冻结列的 `left` 每次重建要重新写（`syncFrozen`）
- 行的「身份」在 DOM 层不存在，只有 `data-id` 这一个字符串替身

## 三、为什么它和「自由录入」天然冲突

「自由录入」的核心是：

> **空行是一个可以随便写、写到一半离开也不会丢的地方。**

在虚拟滚动里，「空行」根本不是实体 —— 它是 `renderWindow()` 在 `i >= rows.length` 时现造的一个 `cloneNode`。于是：

| 用户动作 | 虚拟滚动下发生什么 |
|---|---|
| 在空行写了一半，滚动一下 | 窗口重建，那个 `<tr>` 被销毁，内容没了 |
| 给某行填了金额建单 | `render()` 重建整屏，别的空行全部归零 |
| 切去设置页再切回来 | 重新算 `end`，空行数量都可能变（`clientHeight` 读到 0 时一个都不生成） |
| 空行里写着账户 A，去设置把 A 改名 | 草稿文本还是 A，切回来一失焦就按 A 又建一个账户 |

这四条**全是同一条账**：行不是实体。

今晚打的四个补丁，正好一一对应：

1. `draftRows` —— 给空行内容找了个存身之处（因为 DOM 存不住）
2. `clientHeight || 800` —— 给视口高度找了个兜底（因为读到 0 就什么都不渲染）
3. `renameBlankDraft` —— 账户改名时手动同步草稿（因为没有「行」可以跟着改）
4. `clearBlankDraft` —— 建单时手动消费草稿（因为那行已经不是空行了）

**每加一个编辑特性，就是再加一层这样的补丁。**
还没加、但迟早要加的：焦点恢复、IME 组合态、跨窗口框选、数据变化后的滚动锚定。

## 四、它对性能的真实贡献

虚拟滚动的收益是「**恒定** 30 行 DOM，无论数据多少」。代价是「每一行都是临时的」。

关键在于：这个收益在什么场景下才兑现？

| 场景 | 全量渲染 3000 行 | 分批 200 行 | 虚拟滚动 |
|---|---|---|---|
| 打开页面（首屏） | 慢（0.5–1.5 s，移动端更慢） | 快（约 30 ms） | 快（约 30 ms） |
| 往下翻到最早一笔 | 已经全在 DOM，直接滚 | 需要点/滚若干次加载 | 直接滚，始终 30 行 |
| 在中间某行改一个金额 | 快 | 快 | 快（但要保证不重建） |

**注意第二行**：分批追加在「打开」这一步和虚拟滚动一样快。差别只在「一口气翻到底」。

而用户的实际使用是：**打开看最近几笔，往下录新的**。第二行那个场景很少发生，发生了也只是一次几百毫秒的加载。

## 五、边界：什么时候虚拟滚动是必须的

必须用：

- 列表项 **> 1 万**，且用户会**持续滚动浏览**（信息流、日志、聊天记录）
- 行内容很重（图表、图片、富文本）
- **只读**展示，不需要原地编辑

反过来说：

> **需要原地编辑的长列表，几乎都不该用虚拟滚动。**

Excel、Numbers、AG Grid、Google Sheets 都是分批渲染 / 分页，不是虚拟滚动。因为它们的第一公民是「编辑态」，而编辑态必须有稳定的 DOM 宿主。

## 六、单文件版是怎么做的（作为对照）

`personal/index.html` 的流水表：

- 首批 200 行（`FLOW_BATCH = 200`）
- 滚到底 → `IntersectionObserver` 或滚动距离判断 → `appendFlowRows(200)`，**只 append，不重建已有的行**
- 数据全部显示完，才在末尾补空行
- 建单：把当前空行**就地转正**（写 `data-id`、`data-new='0'`、显示删除按钮），末尾再补一个空行 —— **一行都不动别的**

行是真实节点，所以：

- 空行里写的东西不会因为重建消失（没有重建）
- 焦点不会丢
- 改名不需要同步任何「草稿」

它没有用虚拟滚动，用了很多年。

## 七、如果换，换掉的是什么

换的是 `ui/render-transactions.js` 里的「窗口投影」那一层，**不是表格**。

| 项 | 现状 | 换后 |
|---|---|---|
| 对外 API | `renderRows(tbody, rows)` / `patchRow` / `tpl` | 不变 |
| `flow.js` | 调 `renderRows`，用 `rows.length` 算滚动位置 | 改一处：用返回的实际渲染行数 |
| 空行草稿 `draftRows` | 必需 | **可以整个删掉**（行是实体，不需要存） |
| `clientHeight` 兜底 | 必需 | 不需要（没有窗口计算） |
| `renameBlankDraft` | 必需 | 不需要（行还在原地，改名不影响它） |
| 建单 | `render()` 重建整表 | 可以就地转正，也可以保留重建（重建也不丢内容，因为空行是既存节点？—— 不，重建仍会丢，所以还是就地转正更稳） |

**风险点**：200 行 × 6 个 input = 1200 个 input 节点，移动端首屏约 100–200 ms。可接受，但需要实测。

## 八、一句话判断

> 1 万笔、每月 300 笔、日常只看最近几百条 ——
> **虚拟滚动的收益你永远兑现不了，但它收的税你每天都在交。**

换成批追加不是「换一个更聪明的方案」，而是**减少一层抽象**：

- 虚拟滚动 = 为了让「很多行」看起来存在，付出了「行不稳定」的代价
- 分批追加 = 承认「不需要那么多行同时存在」，于是行可以是真的

项目里已经有一条经验（`AGENT-认知备份.md` §八）：

> 凡是「我设计了一套更聪明的方案」，最后都失败了；
> 凡是「照单文件版抄一遍」，都成了。

虚拟滚动就是那个「更聪明的方案」。
