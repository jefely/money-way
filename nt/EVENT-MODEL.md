## 零、网络：节点与边

账本是一张有向网络。每一笔流水是一条边，从转出节点指向转入节点。
节点分成几类：资产、负债、收入、费用、权益，以及成本。类决定这个节点上谁增加余额。
一个节点的余额，就是流过它的净流量。环图把同一张网络画成弧块（节点）和弦（边）。
界面说「节点」。存储字段仍叫 `accounts` / `from_id` / `to_id`，避免把已有账本改掉。

## 一、先校准认知：双极性不是新东西

v4.1 把双极性写成了「新架构」，但 `ACCOUNTING-MODEL.md` 里这条 **2026-10 就已经落地了**：

```js
// core/schema.js —— 全项目唯一的极性定义
export const DEBIT_TYPES = [ACCOUNT_TYPE.ASSET, ACCOUNT_TYPE.EXPENSE, ACCOUNT_TYPE.COST];
```

`core/balance-calculator.js` 的 `balanceOf()` 一年前就在写
`isDebitType(account.type) ? inflow - outflow : outflow - inflow`，
和 v4.1 §1.2 那条「余额 = A极 ? (转入−转出) : (转出−转入)」**逐字等价**。

所以 v4.1 真正新增的只有三样：

| v4.1 的新东西 | 现状 | 落在哪 |
|---|---|---|
| 一条事件挂**多条**连线（多对多） | 新增 | `createEvent` / `splitEvent` |
| **成本类**（实物成本池） | 新增（2026-11 用户定） | `createNode` 自动 `nature:'physical'` |
| 缓冲池 RAW / 逆向事件 / 幽灵重定向 | 新增（原来只会硬删） | `postEvent` / `reverseEvent` / `mergeNode` |

其余是**同一套东西的另一种写法**。别推翻重来 —— 现有 652 条测试、
加密存储、同步、导入导出全挂在 `from_id/to_id` 上。

## 二、⚠ 必须订正的一处：极性属于节点，不属于连线

v4.1 §2.3 把每一笔流转都写成「**B极 → A极**」：

> 建仓：B极(银行卡) → A极(实物_电脑)
> 还款：B极(银行卡) → A极(信用卡)

**这两句的标注是错的**，而且是同一个错，用 v4.1 自己的定义就能自证：

- §2.2 说 A 极包含**资产池**，所以「银行卡」是 A 极；
- 但上面的例子又把「银行卡」标成 B 极。

真正的模型是：**连线有方向，两端各自有极性**。方向（转出→转入）和极性（A/B）是两个独立维度，
组合起来有四种，**四种都合法**：

| 组合 | 例子 | 会计含义 |
|---|---|---|
| **A → A** | 银行卡 → 实物_电脑（建仓）；银行卡 → 餐饮（消费） | 资产内部换形态 / 费用发生 |
| **B → A** | 工资 → 银行卡；信用卡 → 餐饮（刷卡） | 来源变成持有 / 费用发生 |
| **A → B** | 银行卡 → 信用卡（还款） | 资产偿还负债 |
| **B → B** | 新贷款 → 旧贷款（借新还旧） | 负债内部转移 |

v4.1 会得出「恒为 B→A」，多半是从**工资 → 银行卡**这一个例子里归纳的 ——
那个例子里 B→A 恰好成立，套到「银行卡 → 实物」上就矛盾了。

代码里因此**没有任何地方**假设两端极性不同：

```js
// core/calc-engine.js —— 两端各自查极性，不看对方是谁
row.balance = row.polarity ? inflow - outflow : outflow - inflow;
```

## 三、双式恒等：一行代替一张表

全账本只有一条全局约束：

```
Σ(A 极余额) = Σ(B 极余额)
```

它与 `core/validate.js` 的「资产 + 成本 + 费用 = 负债 + 权益 + 收入」**完全等价**，
不是近似、不是另一套标准 —— 把 A = 资产+成本+费用、B = 负债+权益+收入 代进去就是同一个差：

```
ΣA − ΣB = (资产 + 成本 + 费用) − (负债 + 权益 + 收入) = checkAccountingIdentity().diff
```

`doubleEntryCheck()` 返回的 `diff` 和 `checkAccountingIdentity()` 返回的 `diff`
**必须永远是同一个数**，测试里就是拿这个当断言（`calc-engine.test.mjs` 场景②）。

## 四、六种类型：成本类 = 实物成本池

用户 2026-11 定：会计要素从五类扩到六类，加**成本类**。

### 它是什么

**成本类不是「生产成本 / 制造费用」那套工业会计科目**，它是 v4.1 §2.3 的**实物成本池**：
电脑、手机、家具、工具这些「买的时候是资产、用着用着变成费用」的东西。

### 极性

**A 极（`DEBIT_TYPES` 里）**，与资产类同向：转入增加、转出减少。
理由：买电脑那一刻钱没有「花掉」，只是从流动池沉到实物池；它变费用是在折旧那一步。

### 两条硬规则

1. **选了 `type:'成本类'` 就自动是 `nature:'physical'`**，不用再填一遍。
   `createAccount()` 和 `createNode()` 都这样，两处行为必须一致。
2. **残值不落库、只算**。节点上只存 `originalCost`（原值）与 `itemStatus`；
   `residualValue` 每次由 `physicalBook()` 现算。
   存残值等于存第二份事实，迟早和流水对不上 —— 那正是「流水是唯一客观事实」要防的事。

### 原值从哪来

优先取节点上的 `originalCost`；没填就**拿累计转入推断**（买电脑那 10000 的流水本身就是证据）。
`physicalBook()` 用 `costSource: 'field' | 'inferred'` 说明这次用的是哪个 ——
**不要让推断冒充事实**。

### 三个动作（`calc-engine.test.mjs` 场景③）

| 动作 | 连线 | 效果 |
|---|---|---|
| **建仓** | 银行卡 → 实物_电脑 10000 | 实物 +10000；**当期费用不增加** |
| **折旧** | 实物_电脑 → 折旧费用 2000 | 实物 8000；费用 +2000（沉没成本落地） |
| **平仓** | 实物_手机 → 银行卡 3000 ／ → 处置损益 2000 | 实物清零；回款 +3000；变现亏损 +2000 |

平仓那两笔是**同一条事件的两条连线**（合计 = 原值 5000），
`splitEvent` 一次拆完，不需要手工开两条流水。

## 五、事实不可篡改

| 需求 | 做法 | 禁止 |
|---|---|---|
| 录错了 | `voidEvent()` 改状态为 VOID + 记原因 | 删事件 |
| 退款 / 冲销 | `reverseEvent()` 生成**新**事件，连线两端对调，带 `reverses: 原id` | 改原事件、删原事件 |
| 账户合并 | `mergeNode()` 给废弃节点写 `mergedInto`，计算时重定向 | 改历史流水的 `to_id` |
| 改金额 / 改日期 | 作废 + 重开一条 | 原地改 |

`reverseEvent()` / `mergeNode()` 都做了「原对象快照不变」的断言 ——
这不是形式主义：这两个函数最容易被写成「顺手改一下原对象」，一改，历史就没了。

**合并成环**（A→B→A）的处理：环上所有节点**收敛到同一个代表**（字典序最小）。
不能各自停在自己身上 —— 那样 a 解析成 b、b 解析成 a，一条 a→b 会变成自环还查不出来。

## 六、缓冲池：备注即缓冲

v4.1 §2.1「用户输入的咖啡，没有任何数学极性」。落地成两个状态：

| 状态 | 含义 | 参与计算 |
|---|---|---|
| `RAW` | 只有 `rawText` + 金额，没有连线 | **否** |
| `POSTED` | 连线齐了、合计对得上 | 是 |
| `VOID` | 作废，连线和金额保留作证据 | 否 |

**「未分类节点不参与平账」这句话要精确化成**：
真正不参与平账的是 **RAW 事件**；未分类**节点**仍有极性，它参与的连线照样进双式恒等 ——
否则一笔「银行卡 → 未分类」会让 ΣA ≠ ΣB，账就假了。
它不进的是**分类统计**（报表按 `category` 分组时被过滤掉）。

`UNCLASSIFIED_NODE_ID` 目前只是占位常量，还没有任何代码创建它 ——
等「简码 → 名称 → 兜底」那条匹配链接进来时再用。

### 空类型账户（U 区）：类型不填，决不入账 —— ✅ 2026-11 用户裁决

用户原话：**「U 区节点类型如果不填，就决不入账，入账没意义，只会增加混乱。」**

落地在 `core/schema.js` 的 `canPost()` / `syncPostStatus()`：

> 一条流水只有在「两端账户都存在、都有类型、金额 > 0」时才算已入账；
> 否则**写库时**就标 `status:'draft'`。

覆盖全部入口：录入（`addTransaction`）、编辑（`updateTransaction`）、导入、
计划落账（`plan-occurrence`）、期初迁移（`migrateOpeningToTransactions`）、
删账户（`removeAccount`，引用它的流水断链 → 降级）。
补上类型时 `updateAccount` 自动转正；清空类型自动降级。短语草稿只是其中一条路径，不是特例。

**于是空类型的极性不再影响任何数字** —— 它没有入账流水，余额恒为 0。
下面这张表仍然是真的，但已经只是兜底，不再产生可观察的差异：

| 位置 | 空类型 → | 依据 |
|---|---|---|
| `balance-calculator.balanceOf()` | **B 极** | `isDebitType('')` = false |
| `event-engine.polarityOfType('')` | **A 极** | 对齐 `createAccount` 的默认资产类 |
| `opening-tx.openingEnds()` | **A 极**（借方） | 注释写明「空类型按借方（资产壳）处理」 |

`core/ledger-adapter.js` 的投影仍显式传 `isDebitType(type)`（选 B 极），
因为对账的对象是**旧模型的既有结果**（旧账里确实存在「空类型 + 已入账」的脏数据）；
节点上同时打 `untyped: true`，让统计层仍能把它归回 U 区。

> 顺带修掉一个连带 bug：`createAccount()` 对空类型默认「资产类」，而 `updateAccount()`
> 走的是同一个工厂 —— **给 U 区账户改个名字，它就会悄悄变成资产类**，流水跟着入账。
> 现在 `updateAccount()` 保留空类型语义（默认资产类只适用于新建）。

## 七、和现行规范的冲突（颜色已裁决 · 线宽待拍板 · 三层环未做）

### 7.1 线宽：金额 vs 类型权重 —— ⏳ 仍未裁决

| | v4.1 §4.3 | 现行 `MONEYWAY-SPEC.md` §3.1 |
|---|---|---|
| 线宽表示 | **发生金额**（比例缩放） | **转入账户类型**的权重（费用 4× / 资产 3× / 负债 2× / 权益收入 1×） |
| 用户的话 | 「修正线宽骗局」 | 「终点优先，越接近钱花掉的地方越粗」 |

两者**不可共存**：一根线宽不能既是金额又是类型权重。
现行实现是 `strokeWidth = unitArcLen × 0.8 × weight`，**金额信息完全不在线宽里**。

> **2026-11 的新情况**：弧段本身已经能按金额切了（第二套粒度模式，见 §8），
> 于是「弧段宽 = 金额，线宽 = 类型权重」这个组合会越来越别扭 ——
> 弧段明明按金额变了，线宽却还按类型查表。
> 我的判断仍是 v4.1 对：金额是客观事实，类型权重是解释，
> 让解释盖住事实正好违反「视觉引擎绝不能凌驾于会计逻辑之上」。
> 但改它要重排 `mw-path-calculator.js` 的整套线宽表 + 重定「同目标多线叠压」，
> **改之前要你点头。**

### 7.2 颜色：黄金角 vs 24 色 maximin —— ✅ 已裁决（2026-11）：保持 maximin

v4.1 §6.2 曾提议用 `hue = hash(id) × 137.5°` 生成「全局绝对唯一」的色相。
但 `MONEYWAY-SPEC.md` §3.3 早就**明确否决过这个做法**，理由写在代码注释里：

> 分类到 10 个左右时，第 1 个和第 9 个会撞成两个差不多的绿色
> （137.5° 与 283.5° 的补角），用户实测「两个绿色是一对，线也几乎同色，分不清」。

现行是离线贪心 maximin 挑的 24 色表，任意两色 CIELAB ΔE76 ≥ 24，且**每个前缀都是好分布**。
黄金角是「数学上均匀、感知上不均匀」的典型 —— 色相环在感知上不是等距的。

**用户已定：保持 24 色 maximin，黄金角不采用。** 这是本项目少数「实测推翻设计」的记录。

### 7.3 三层嵌套环：做了，又主动砍回两层

`graph/mw-layers.js` 实现了三层同心环的几何：三层**共用同一套角度**
（外层和中层是内层的聚合视图，不另算角度，边界天然对齐）。
但 2026-11 把**中层（统计分类）拿掉了** —— 分类在角度上本来就有 0.8° 的缝，
再画一圈同色系分类带等于把「分类边界」说两遍，还多出一整圈颜色。
现在外层只留一条 6% 宽的细线表示六大类型。

所以这条的准确状态是 🔁（实现后主动简化），不是 ❌「未做」。
中层要不要恢复、恢复到什么粒度，等 7.1 定了线宽再谈 ——
线宽语义没定，三层环画出来还是错的。

## 九、渐进式草稿（流水 status，不替换事件引擎）

2026-11 的「从一杯咖啡开始」走的是 **`state.transactions`**，不是上面的事件引擎。
事件层的 RAW / POSTED 继续只服务 `createEvent`，**不要**把流水换成事件，也不要接云端或端侧大模型，不加标签组，不新增第 7 种账户类型。

规则（实现以这里为准；设计稿里「饮品自动长成节点」「失焦丢掉草稿」这两处已订正）：

1. 草稿流水带 `status:'draft'`。缺 `status` = 已入账，旧数据不用迁移。
2. 余额、统计、会计恒等式、环网图、同步二维码只吃已入账流水。校验把草稿单独计数，不算 V1。
3. 草稿变成已入账的条件：两端都在，且两个账户都有类型，金额 > 0。单边支出不进余额。
4. 认不出的词用现成的 `ensureAccountByText` 建空类型账户（U 区）。只有支付账户的**精确**词库命中（微信、支付宝……）预填类型「资产类」+ 分类「网络账户」。模糊命中只出候选，不自动建有类型的账户。
5. 短语（咖啡）进备注字符串。不从分类名（饮品）自动建账户。
6. 用户事后补上账户类型时，两端齐全的草稿自动入账。
7. 学到的「短语 → accountId」放在 `state.mappings`，跟账本一起加密，并写进加密备份。
8. 一句话输入条的「当前引导」只认它自己创建的那条草稿 id：那条草稿被删掉、或已经补全入账后，
   下一次流水重画（或手动编辑）就把引导归零，回到「随手记一笔，草稿会留下。」，
   **不猜**其它草稿该不该接。删掉草稿 = 重新开始引导（用户 2026-11 报「删了还在问哪里付的钱」）。
9. 每月固定收支自动落账时，备注只取**固定表模板的备注**，模板为空就为空；
   只有带 `inst` 的分期才有「分期还款 第 n/m 期」。虚拟固定行也不再用月份 key 拼「第几期」。
10. **U 区（空类型）账户的流水一律不入账**（2026-11 用户裁决，见 §六 末尾）。
    入账条件收紧为「两端账户都存在、都有类型、金额 > 0」，由 `schema.syncPostStatus()`
    在**写库时**定状态：缺类型 / 断链 / 零额 → 草稿；补上类型 → 自动转正；
    清空类型或删账户 → 自动降级。所以「未分类」不再是一个能进余额的中间态。

词库是扁平的 `{keyword, accountName, type, category, role}`，大约 150–200 个词。
解析器 `parsePhrase` 先剥整天词（今天 / 昨天 / 前天、11月4日、ISO），再按最长优先、每个名字只用一次（用户账户优先于词库）认账户，金额取剩下文本里的最后一个数（含 50元 / 50块 / ¥50），其余是备注。停用词按整词剔除，避免拆开花呗、支付宝、费用。简码后面可以紧跟金额：`ZC50` = 简码 ZC + 50（纯数字简码不享受这条边界放宽）。

失焦和 30 秒无输入只收起候选，**不删除**已经写下的草稿。
